C++ vshard Router vs Lua vshard Router — Equivalence Analysis

Detailed comparison of behavioral deviations between the C++ userver implementation and the reference Lua vshard router

Reference: tsafin/userver PR#3 · tarantool/vshard master · vshard/error.lua · vshard/router/init.lua · vshard/consts.lua

Current State

This HTML report is historical background and is not a line-by-line current status sheet anymore.

The current verified state is:

  • 71 tests pass in the vshard functional suite.
  • The C++ proxy now matches Lua closely for the tested IPROTO router API on Tarantool 2.6.0.
  • Most formerly open gaps in call parsing, error envelopes, discovery, map_callrw, rebalance paths, bootstrap, sync, info, and routeall have been closed.
  • The main remaining gaps are degraded-cluster info() parity and true return_raw support on newer Tarantool runtimes with msgpack-object support.

For the current up-to-date review, use tarantool/vshard/lua_cpp_semantic_review.md.

1 — Topology Discovery & RefreshFull

Area Lua vshard (reference) C++ implementation Impact Sev
RefreshFull strategy Background discovery fiber calls vshard.storage.buckets_discovery on every RS iteratively, building the full route_map. Bucket→RS mapping is entirely driven by what the storages report. Probes only bucket 1 and bucket_count/2+1, then extrapolates a contiguous-range split across all known RS. Fixed in topology_fetcher.cpp:185. Correctness failure for ≥3 RS clusters. After any RefreshFull the routing table can route large ranges to the wrong RS — opposite of healing. WRONG_BUCKET storm becomes permanent until restart. P0 OPEN
Discovery scope on unknown bucket When bucket is unknown, Lua calls bucket_stat on all RS until it finds the owner (bucket_discovery()). Scans every replicaset. No equivalent bucket_stat scan across all RS. Unknown bucket → triggers rate-limited RefreshFull, which itself is broken for N>2 RS (see above). Unknown buckets may never resolve for N>2 RS. Lua falls back to scan; C++ falls back to broken two-probe refresh. P1
RefreshFull rate-limit scope Discovery fiber runs continuously; rate limiting is per-RS via exponential backoff on connection errors. Single global 1s rate-limit on last_moved_refresh_. All concurrent fibers benefit once one fires it — stated as intentional in commit message. Rate-limit logic is correct in intent but the underlying RefreshFull is still broken (see #1). Also the 1s floor is a hardcoded constant vs Lua's data-driven backoff. P2
BUCKET_IS_LOCKED handling router_call_impl handles code BUCKET_IS_LOCKED the same as WRONG_BUCKET: calls bucket_reset and retries with destination. vshard_error.hpp / vshard_error.cpp do not define or handle BUCKET_IS_LOCKED (no such VshardErrorType). It would be treated as an unknown error and propagated to the client. Requests during internal bucket locking (admin operations, forced moves) fail instead of retrying. Not a common path but fully observable under manual rebalancing. P2

2 — Public API: vshard.router.call* parsing

Area Lua vshard (reference) C++ implementation Impact Sev
vshard.router.call generic signature call(bucket_id, mode, func, args, opts) where mode is the second positional arg. callrw/callro/callre/callbro/callbre are convenience wrappers that fill in mode. ParseVshardRouterArgs assumes the 3-tuple shape [bucket_id, func_name, args_array] and routes generic vshard.router.call through the same parser — mode is read as func_name. Any client calling the generic vshard.router.call(bid, 'write', 'myfunc', {...}) gets the string 'write' dispatched as the function name and 'myfunc' as args. Every such call fails with a procedure-not-found or corrupted result. P0 OPEN
callbro / callbre routing semantics callbro = mode='read', balance=true. callbre = mode='read', balance=true, prefer_replica=true. Different replica-selection logic from plain callro. Both names accepted in the dispatch list but routed to plain kReadOnly mode — no balance or prefer_replica flag is set or propagated. Zone/weight-based load balancing silently broken. Under zone weighting or replica outages the proxy can pick a different node than net.box would, or fall back to master when caller explicitly requested replica-preferred path. P1 OPEN
callre routing semantics callre = mode='read', prefer_replica=true. Tries replicas first, falls back to master only after all replicas are exhausted. Accepted and routed as plain kReadOnly. prefer_replica semantics not implemented. Falls back to master as soon as no ready replica is cached. Applications relying on callre to keep read load off the master won't get the expected behavior. Functionally incorrect but rarely catastrophic. P2
opts.timeout / per-call timeout router_call_impl reads opts.timeout (default: CALL_TIMEOUT_MIN = 0.5s) and uses a deadline-based retry loop. Retries stop when deadline is exceeded. No per-call timeout from the IPROTO client request. retry_count_ caps retries; no wall-clock deadline enforcement visible in the retry loop. Long-duration retries can silently hold client connections far past what the application expects. No client-visible timeout behavior on the router hop. P1
opts.return_raw opts.return_raw = true returns raw msgpack objects, skipping Lua deserialization. Documented API option. Not parsed. Opts struct is entirely ignored/dropped at the IPROTO server layer. Clients using return_raw for performance (large result sets) get decoded results. Not a correctness bug; a performance/API coverage gap. P3

3 — Error Handling & Retry Semantics

Area Lua vshard (reference) C++ implementation Impact Sev
WRONG_BUCKET retry on missing destination If err.destination == nil, calls bucket_reset (clears local entry) and re-enters discovery via the background fiber. Does NOT directly call bucket_stat scan immediately in the hot path. If destination key is absent (IsMissing), the pre-fix code called PatchBucketOwner("") silently. Fixed in commit b4bac7b. Post-fix: calls RefreshFull, but RefreshFull is still broken for N>2 RS. Post-fix is structurally correct but relies on broken RefreshFull. See §1. P1
NON_MASTER retry Calls bucket_reset and triggers failover fiber to re-identify master. The retry uses the updated master from the replicaset's internal failover state. Calls RefreshFromStorage(rs) to re-probe the specific RS's master. Single-RS probe is correct for this case. Behaviorally correct for the 2-RS case tested. Minor: doesn't handle the edge case where the RS itself is partitioned (Lua falls back to discovery). P3
TRANSFER_IS_IN_PROGRESS retry Calls bucket_reset, waits a small interval (CALL_TIMEOUT_MIN * 2^n exponential backoff up to CALL_TIMEOUT_MAX = 64s) and retries. Retries immediately without backoff. PR commit message says "back off, retry" in description but no sleep/backoff is visible — just increments retry counter and loops. Under active bucket migration, the C++ proxy generates a tight retry storm toward the storage that is busy transferring. Can amplify load on the storage node exactly when it is most stressed. P1 OPEN
Retry count vs deadline Retry loop is deadline-based. No fixed retry count. Retries continue until fiber.clock() >= deadline. Fixed kMaxRetries (from settings). Deadline not checked. A cluster with many bucket migrations could hit the cap before the request succeeds. Two different failure modes: Lua might retry too long; C++ might give up too early. Different observable SLA behavior for the same cluster event. P2
Error code parsing: name fallback Errors always carry both .code (int) and .name (string). Router checks .code numerically. Post-fix (b4bac7b) added ErrorTypeFromName() fallback. Correct codes 1/2/7/9 are now used. FIXED Fixed in the PR. Was a critical bug earlier (all WRONG_BUCKET retries were silently no-ops). ✓ Fixed

4 — Replica Selection & Connection Pool

Area Lua vshard (reference) C++ implementation Impact Sev
Replica priority list (zone weights) Per-replicaset priority_list ordered by cfg.weights distance from current zone. callro/callre walks the list in priority order, skipping down replicas. Round-robin across all replicas for kReadOnly. No zone concept. No weights parameter. Geographic/zone-aware routing unavailable. Requests may cross DCs unnecessarily. Acceptable for single-DC deployments; a correctness gap for multi-DC. P3
Adaptive network timeout network_timeout per replica: updated on every 10th success (+) and every 2nd failure (-). Dynamic congestion-sensitive timeout. Fixed timeout from static_config.yaml. No adaptive adjustment. Under congestion, the C++ proxy either times out too aggressively or too leniently. No automatic calibration. P3
Replicaset backoff / REPLICASET_IN_BACKOFF Recent Lua versions add per-replicaset backoff state. Discovery skips RS in backoff (err.code == REPLICASET_IN_BACKOFF). No backoff state per RS. Unhealthy RS are probed on every request until they respond or timeout. Under partial RS failure, C++ generates more failed probes than necessary. No correctness issue; latency/throughput impact. P2
map_callrw (scatter/reduce) Full vshard.router.map_callrw: consistent map-reduce with storage refs, prevents bucket migration during scatter phase, collects all RS results. vshard.router.map_callrw is now exposed over IPROTO and keeps storage_ref and storage_map on the same Tarantool session per replicaset. Partial bucket_ids routing uses live discovery. Plain differential parity is now covered. The remaining unverified part is behavior under active rebalancing while refs are held. P2

6 — Equivalence Proof Strategy

6.1 — Can formal equivalence be proved?

Full formal equivalence is not achievable without fixing the known behavioral gaps first. After fixing the P0/P1 items, three complementary approaches can establish high confidence:

A. Protocol-Level Differential Testing

Run both the Lua router and the C++ proxy in front of the same vshard cluster. Send identical IPROTO request streams to both. Compare responses byte-for-byte (ignoring sync IDs). This catches any encoding, routing, or retry divergence.

  • Tool: existing bench_vshard.lua adapted as a diff harness
  • Scenarios: normal calls, mid-migration calls, RS failure, master failover
  • Automated using tarantool-test-run + two router endpoints

B. Reuse vshard's Own Integration Test Suite

The tarantool/vshard repo has a full integration test suite under test/router/. These tests drive the router via net.box IPROTO calls — the same interface the C++ proxy exposes. By pointing test/router/*.test.lua at the C++ proxy instead of the Lua router, deviations surface as test failures.

  • Directly applicable tests: router.test.lua, retry_reads.test.lua, exponential_timeout.test.lua, master_discovery.test.lua
  • Requires: C++ proxy listening on same port as Lua router in test env

C. Property-Based Testing of Routing Table

The RoutingTable and RefreshFull logic can be property-tested in isolation. Key invariant: for any cluster configuration (N RS, arbitrary bucket assignments), after RefreshFull, FindReplicaset(b) must return the RS that actually owns bucket b.

  • Fuzz bucket ownership assignments, run RefreshFull, assert correctness
  • Already has unit test infrastructure in vshard_test.cpp — extend it

D. State Machine Equivalence (Long-term)

Model both routers as state machines over the routing table state and compare reachable states under the same event sequences. Practical approach: use IPROTO_WATCH to observe bucket ownership changes on storages and verify both routers converge to the same table state after each event.

  • Most rigorous but highest effort
  • vshard's test_run framework can inject events programmatically

6.3 — Recommended Fix Priority Order

  • Fix 1 (P0): Replace two-probe heuristic in RefreshFull with a proper scan: for each known RS master, call vshard.storage.buckets_discovery({from=1}) iteratively (or bucket_stat on a representative spread) until all bucket_count buckets are mapped.
  • Fix 2 (P0): Add mode-arg parsing for generic vshard.router.call: detect 5-tuple shape [bucket_id, mode_str, func, args, opts] vs 3-tuple shape used by callrw/callro.
  • Fix 3 (P1): Add per-call deadline tracking. Read opts.timeout from the IPROTO request (or default to CALL_TIMEOUT_MIN) and enforce it as a deadline in the retry loop.
  • Fix 4 (P1): Add exponential backoff sleep on TRANSFER_IS_IN_PROGRESS: start at CALL_TIMEOUT_MIN/2, double per retry, cap at CALL_TIMEOUT_MAX.
  • Fix 5 (P1): Add BUCKET_IS_LOCKED to VshardErrorType and treat it identically to WRONG_BUCKET.
  • Fix 6 (P1): Implement prefer_replica and balance flags for callre/callbro/callbre.
  • Fix 7 (P1): Implement storage ref protocol in MapCallRW (vshard.storage.ref/vshard.storage.unref + vshard.storage.map).
