# Proxy CPU experiments: alternatives evaluated and the decision

**Date:** 2026-10-23 · **Baseline:** `ac632e6f6` (Phase 1c+2 + wakeup
elision + spinlocks + direct reply staging; 2.0-4.3 cpu-ms per 1000 ops
depending on load, ~140-150k ops/s aggregate on the 8-master stand).

**Question:** can we further reduce the CPU the proxy burns per request?
The perf profile says proxy CPU is ~80% userver scheduler machinery
(`TaskContext::DoStep` + `jump_fcontext` + wait-list bookkeeping +
moodycamel queue ops + detached-task accounting) and only single-digit
percentages of actual msgpack/protocol work. Four families of
alternatives were evaluated.

---

## E1 — scheduler configuration (no code)  → NO EFFECT
`spinning-iterations` (100/1000/2000/4000) and `worker_threads`
(2/3/4/6) swept. Medians overlap for all values; the saturated-WSL2 noise
floor (±30% run-to-run) hides everything. **Keep defaults.**
Worktree: `../wt-e1-spinning` (branch `exp/e1-spinning`, EXPERIMENTS.md).

## E2 — inline pending entries (Phase 3a)  → BELOW MEASUREMENT FLOOR
`make_shared<PendingEntry>` per request ≈ 40-80 ns ≈ 2-4% of CPU/op.
Correctness is achievable (slot-owned storage, result copy + Send under
`pending_mutex_`, caller clears the slot) but the payoff cannot be
measured on this stand. **Deferred** until an execution-model change
redesigns that storage anyway.
Worktree: `../wt-e2-inline` (branch `exp/e2-inline-slots`, EXPERIMENTS.md).

## E3 — persistent handler-coroutine pool  → IMPLEMENTED, VALIDATED, REJECTED
Full implementation on branch `exp/e3-handler-pool` (worktree
`../wt-e3-handlerpool`, EXPERIMENTS.md): WorkQueue (Mutex + CV), lazy
persistent handlers ("reader pushes, spawns only when none parked"),
semaphore token transferred with the work item, drain/close/join
protocol. 169/169 tests, byte-identical responses, 148-149k ops/s with 0
errors. **Medians: 416-433 ticks vs baseline 420-439 — no measurable
difference.** The CV park/wake cycle costs the same as the task spawn it
replaces. **Rejected: complexity without gain; keep per-request detached
tasks (HEAD).**

## E4 — execution-model alternatives (analysis, not implementable in scope)

| Option | Removes | One-time cost | Expected CPU/op |
|---|---|---|---|
| C++20 stackless coroutines (rewrite connector) | coroutine stacks, context switches — state machines generated by the compiler | 4-8 wks, mechanical but large | 2-3x less scheduler cost |
| Callback/state-machine style (Seastar-like, no coroutines) | all coroutine overhead | 8+ wks, "callback hell" | 3-5x less |
| **Thread-per-core + io_uring** (own event loop outside userver for the proxy) | cross-thread wakeups entirely, all locks, epoll+recv/send syscalls (multishot recv, provided buffers, SQPOLL) | 6-10 wks, new runtime | 5-10x less; the only path that scales to 1M per node |
| io_uring inside userver | syscalls only | framework-level effort (userver has io_uring for file I/O only) | syscall share only (~30% of the remainder) |
| Linux tuning (busy_poll, IRQ/worker affinity, isolcpus) | interrupt/wakeup jitter | hours | 10-20%, needs bare metal |
| Kernel bypass (AF_XDP) | TCP stack | very high | radical, out of scope |

## DECISION

1. **Keep the proxy as-is at `ac632e6f6`.** Every measurable in-framework
   lever has been pulled: buffered IO, write coalescing, concurrent
   request handling, single-copy forwarding, wakeup elision, spinlocks,
   direct reply staging. Pool/config micro-tuning shows no measurable
   gain; it is rejected to preserve simplicity.
2. **Proxy CPU per request is now framework-intrinsic.** Further
   reduction requires changing the execution model, not tuning userver:
   the candidate worth committing to is a **standalone thread-per-core
   proxy with io_uring** (option E4.3), kept as a future project; its
   IPROTO handling is already isolated in `iproto_server.cpp` +
   `Connection`, so the protocol layer ports over.
3. **Reaching 1M ops/s** on the current codebase requires hardware, not
   code: measured storage ceiling ~100k/master (73k with WAL, 130k+ with
   wal_mode=none per 2 masters ⇒ ~150k aggregate on this box is CPU-bound
   across proxy+9 tarantool+loadgen). N masters on N real cores ≈
   80-100k×N; 10-12 masters on bare metal reach ~1M with the existing
   proxy.

## Measurement methodology (for future re-runs)
`/tmp/measure_cpu.sh BIN TAG [conns depth ops reps]` — proxy CPU time
(/proc/PID/stat utime+stime) over fixed 200k-op runs via the pipelined
loadgen, min/median of N runs, single proxy instance on the port (verify
`ss -tlnp | grep 13306` — SO_REUSEPORT stacks instances silently).
Only same-context interleaved A/B comparisons are meaningful on this box.
